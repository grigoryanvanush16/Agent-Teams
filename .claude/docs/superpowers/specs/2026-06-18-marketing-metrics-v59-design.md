# Маркетинг метрики v1 (формат v58) — единый файл метрик, витрин и дашбордов

**Дата:** 2026-06-18
**Статус:** на ревью
**Автор:** Vanush + Claude

## Цель

Собрать один Excel в формате «ИБ метрики v58», но для маркетинга. В нём: каталог
маркетинговых метрик (верифицированный Ксенией + вытащенный из реальных дашбордов),
roadmap витрин под эти метрики, детальные спеки ключевых витрин по полям, ТЗ для DE,
реестр всех маркетинговых дашбордов и топ-10 дашбордов для перевода на новую парадигму
DWH. По каждой метрике и дашборду фиксируется судьба: **авто в DWH** / **пересобрать в
рамках реформы** / **считается на стороне BI** / **архив**.

Файл — рабочая основа реформы маркетинговой аналитики: из него DE берёт, что строить,
а маркетинг видит, какие метрики и где живут.

## Структура файла — 6 листов

### Лист 1. Каталог метрик
Формат v58 один-в-один:
`Группа │ № │ Метрика │ Гранулярность │ Описание │ Формула (словами) │ Ед. │ Приоритет (0/1) │ KPI (Да/Нет) │ Статус │ Судьба │ Источник-витрина │ Витрины в расчёте`

- Наполнение: 36 метрик Ксении (операционная воронка) + метрики из дашбордов (визиты,
  CR визит→лид, квал-лиды, ДРР, CPS, ROMI, портрет клиента, дозвон, самооплаты, когорты).
- Колонка **Судьба**: `авто в DWH` / `пересобрать` / `BI-сторона` / `архив`.
- Дубли мер (56 в «Статистике по лидам», 141 в «Метриках продаж») сводятся к базовым с
  пометкой «дедупликация».
- Статус: `Готово` / `В работе` / `GAP` / `Нет данных`.

### Лист 2. Roadmap витрин
`Витрина/таблица │ Статус │ Приоритет │ Ответственный │ Источник (БД) │ Судьба │ Комментарий`

Кандидаты витрин: `dm_marketing_funnel` (ядро D1), `dm_leads_distribution`,
`dm_self_payments`, `dim_channel`, `dim_campaign` (utm), `dim_client_profile` (портрет),
`stg_ad_spend` (расход кабинетов), `stg_metrika_visits` (визиты в БД), `dm_cohort_conversion`,
`dm_callcenter_reach` (дозвон).

### Лист 3. Спеки витрин (по полям)
Для ключевых витрин (минимум `dm_marketing_funnel`, `dim_channel`, `dim_campaign`,
`dm_self_payments`) — блок SQL над таблицей + поля:
`поле │ описание │ комментарий │ значения (пример) │ ключ │ вопросы │ sql`

### Лист 4. ТЗ для разработки
`# │ Задача │ Что построить │ Какие метрики разблокирует │ Источник/референс`

Ключевые задачи: визиты Метрики в БД (MP-12608), свод расхода кабинетов с воронкой,
дедупликация мер, добавление ROMI, признак квалификации из `lead_load_info`.

### Лист 5. Реестр дашбордов
`Дашборд │ Движок │ Ссылка │ Папка/автор │ Используется │ Назначение │ Ключевые метрики │ Источники данных │ Судьба`

Весь каталог из Google Sheet (ссылки от Vanush) + PBIRS-перечисление + 3 Титовских.

### Лист 6. Топ-10 дашбордов
`Ранг │ Дашборд │ Почему в топе │ Метрики │ Витрины-источники │ Действие │ Приоритет`

## Подход к разбору дашбордов

1. Перечислить нужные отчёты в каталоге PBIRS (через MCP `moedelo-db`, source=pbirs),
   получить ItemID и пути.
2. Вытащить `.pbix` из Report Server (как в аудите 2026-06-03 — извлечение из PBIRS),
   распарсить DataModel: DAX-меры, таблицы, M-запросы (источники).
3. Локальные `.pbix` (часть уже в Downloads) — парсить напрямую.
4. По Сквозной — только листы «исходник лиды» и «исходник продажи».
5. По Титовскому — только 3 названных.
6. Где `.pbix` недоступен — восстановить меры из owox/backoffice через MCP.

## Методология топ-10 дашбордов

Ранжирование по трём факторам: **реальное использование × бизнес-ценность ×
готовность данных**. По каждому — действие:
- `авто в DWH` — источники в owox/backoffice, логика стабильна (лиды, оплаты, выручка, CR).
- `пересобрать` — нужна дедупликация мер / добавление ROMI / перевод визитов в БД.
- `архив` — не используется (напр. Дозвон по операторам, по словам Ксении).

## Авто в DWH vs пересобрать (правило)

- **Авто**: метрика, у которой источник уже в DWH-доступных базах и определение
  однозначно. Переносится в витрину как есть.
- **Пересобрать**: метрика с дублями (56→20), без единого определения, требующая ROMI /
  свода расхода с воронкой / визитов из API в БД.
- **BI-сторона**: справочные срезы, считаемые поверх CH/витрин в PBI/DataLens.

## Открытые вопросы (в ТЗ для DE)

- Точные имена полей источников (поток 1, подтвердить с DE).
- Визиты сайта в БД — блокер MP-12608.
- Системный источник расхода рекламных кабинетов (сейчас ручная выгрузка).
- Признак квалификации: брать `lead_load_info.is_qualified` / `funnel_code`.

## Что НЕ делаем (YAGNI)

- Не строим сами витрины/SQL в БД — только спеки и ТЗ.
- Не трогаем меры колл-центра («Метрики продаж», «Квалификация КД») кроме дозвона —
  к маркетингу не относятся.
- Не изобретаем определения — берём из глоссария Ксении и существующих отчётов.
